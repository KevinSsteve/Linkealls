Quero que você faça agora uma **AUDITORIA COMPLETA DE UI/UX + ENGENHARIA DE DESIGN** em toda a aplicação mobile.

As telas anexadas mostram que as melhorias anteriores foram aplicadas apenas parcialmente. Portanto, **não faça mais um pequeno ajuste visual página por página**.

Quero que você revise o sistema inteiro e corrija os princípios de design que estão causando esses problemas.

O objetivo é transformar a aplicação em um produto mobile **premium, consistente, profissional e com comportamento de app real**, e não apenas uma página web responsiva.

# 2. PROBLEMA CRÍTICO: VIEW MODE VS EDIT MODE

Este é um dos problemas conceituais mais importantes.

A aplicação atualmente mistura visualização com edição.

Por exemplo, na página de perfil do negócio, a descrição aparece ocupando a largura inteira e visualmente parece um campo aberto para edição.

Isso é incorreto.

### REGRA:

Quando o utilizador está apenas visualizando o negócio:

**NÃO mostrar inputs, textareas ou aparência de formulário.**

Mostrar conteúdo como conteúdo.

Exemplo:

DESCRIÇÃO

A Electro Panga é uma loja especializada na comercialização de material elétrico...

Isso deve parecer um texto de perfil.

Não deve parecer:

[ A Electro Panga é uma loja... ]

como se fosse um textarea.

---

# 3. SEPARAR EXPLICITAMENTE OS ESTADOS

Todo componente que pode ser editado deve ter estados claramente separados:

### VIEW

Modo de visualização.

Exemplo:

Descrição

A Electro Panga é uma loja especializada...

### EDIT

Modo de edição.

Exemplo:

Descrição

┌──────────────────────────┐
│ A Electro Panga...       │
│                          │
└──────────────────────────┘

Cancelar     Guardar

Nunca misturar os dois estados.

---

# 4. INFORMAÇÃO NÃO É INPUT

Aplicar esta regra em toda a aplicação.

Se o utilizador não está editando algo:

NÃO usar:

* input
* textarea
* placeholder
* borda de formulário
* cursor de edição
* aparência de campo vazio

Usar:

* texto
* label
* ícone
* divider
* botão de ação

---

# 5. PLACEHOLDER NÃO DEVE SER USADO COMO CONTEÚDO

Este é outro problema importante.

Textos como:

"Adicionar endereço..."
"Adicionar horário..."
"Adicionar contacto..."
"Adicionar e-mail..."
"Pesquisar..."

têm significados diferentes.

"Pesquisar..." pode ser placeholder porque está dentro de um campo de pesquisa.

Mas:

"Adicionar endereço..."

não deve parecer um placeholder gigante de formulário quando estamos no modo de visualização.

Em VIEW MODE usar:

Endereço

Não adicionado

Adicionar endereço →

ou:

Endereço

Adicionar

com aparência de estado vazio + ação.

Quando clicado, aí sim abrir o editor.

---

Criar uma linguagem visual consistente para dados ainda não configurados.

Exemplo:

ENDEREÇO

Adicionar endereço

Não transformar o estado vazio em um input gigante.

Aplicar a mesma lógica para:

* telefone
* email
* website
* horário
* descrição
* catálogo
* campanhas
* conversas
* etc.

---

# 7. CONCEITO DE CONTAINER

Atualmente existem muitos elementos que parecem:

CARD DENTRO DE CARD DENTRO DE CARD.

Isso cria aparência de dashboard genérico.

Estabelecer uma regra:

### Usar CARD somente quando existir uma razão semântica.

Cards podem representar:

* entidade independente
* produto
* campanha
* estatística
* ação importante
* conteúdo agrupado

Não usar card simplesmente porque "precisamos colocar um container".

Informações relacionadas podem simplesmente existir em uma superfície contínua com divisores.

---

# 8. CONCEITO DE SECTION

Uma seção deve ser visualmente reconhecível.

Estrutura:

SECTION TITLE

conteúdo

divider

SECTION TITLE

conteúdo

Não colocar uma borda arredondada em cada pequeno bloco.

---

# 9. MARGENS DAS BORDAS — CORRIGIR GLOBALMENTE

Este problema ainda não foi resolvido.

Na screenshot existem elementos literalmente encostando na borda da tela.

Isso precisa ser corrigido em **todas as páginas**.

Criar um token global:

--page-padding-mobile

Usar aproximadamente:

16 px em telas pequenas

20 px em telas médias

24 px quando houver espaço suficiente

Mas atenção:

não quero simplesmente colocar `padding: 16px` em tudo.

Existem componentes que devem ser edge-to-edge.

Portanto estabelecer regras.

### Conteúdo principal

16–24 px de margem.

### Listas

Podem ser full width, mas o conteúdo interno deve respeitar o gutter.

### Dividers

Podem ser full width.

### Bottom navigation

Full width.

### Cards

Não devem ficar colados ao viewport.

### Search

Respeitar gutter.

### Títulos

Respeitar exatamente o mesmo gutter do conteúdo.

---

# 10. CRIAR UM GRID/GUTTER GLOBAL

Quero que exista uma linha vertical imaginária consistente.

Exemplo:

| 16px | CONTEÚDO | 16px |

O título deve começar no mesmo ponto.

A search bar deve começar no mesmo ponto.

As seções devem começar no mesmo ponto.

Os cards devem começar no mesmo ponto.

Os textos devem respeitar o mesmo sistema.

Não quero:

Título → 0 px

Search → 2 px

Card → 8 px

Texto → 16 px

Isso cria uma sensação de produto mal acabado.

---

# 11. EXCEÇÕES EDGE-TO-EDGE

Alguns elementos podem ocupar a largura inteira:

* listas
* dividers
* bottom navigation
* tabs
* barras de progresso
* imagens específicas
* headers específicos

Mas o conteúdo interno deve continuar alinhado ao grid.

# 12. BOTTOM NAVIGATION

Revisar completamente o footer/bottom navigation.

A barra inferior atual ainda parece pesada e ocupa demasiado espaço visual.

Quero uma bottom navigation com qualidade de aplicativo nativo.

Ela deve:

* ocupar apenas o espaço necessário
* respeitar safe area
* ter altura consistente
* ter ícones de tamanho consistente
* ter labels pequenos
* ter estado ativo elegante
* não parecer uma grande barra de dashboard

Estrutura:

ícone

label

Não exagerar no background verde.

O item ativo pode usar:

verde no ícone
verde no texto

e, se necessário, um pequeno background suave.

Não utilizar uma enorme cápsula verde.

---

# 13. SAFE AREA

Também considerar:

`env(safe-area-inset-top)`

Testar em:

* Android com navigation bar
* Android com gesture navigation
* iPhone com notch

# 35. AUDITORIA VISUAL FINAL

Depois da implementação, percorra TODA a aplicação como se fosse um designer de produto.

Para cada tela pergunte:

1. O conteúdo está alinhado?
2. Existe espaço suficiente nas bordas?
3. Existe algum elemento encostado na tela?
4. Estou vendo um formulário onde deveria existir apenas informação?
5. Existe algum card desnecessário?
6. Existe algum placeholder sendo usado incorretamente?
7. Os títulos possuem hierarquia?
8. Os ícones têm o mesmo estilo?
9. Os elementos têm alturas consistentes?
10. A bottom navigation está correta?
11. O usuário sabe o que pode clicar?
12. O estado atual está claro?
13. Os componentes parecem pertencer ao mesmo produto?
14. Existe espaço vazio excessivo?
15. Existe conteúdo comprimido demais?
16. Existe algum overflow?
17. A interface parece um app mobile real?

# 37. RESULTADO ESPERADO

Quero que, depois desta revisão, a aplicação tenha uma linguagem visual única.

A sensação deve ser:

**"Este é um aplicativo profissional de gestão de negócios."**

e não:

**"Este é um website responsivo feito com vários cards."**

O nível de acabamento deve se aproximar de produtos como:

* WhatsApp Business
* Linear
* Stripe
* Notion
* Apple

Sem copiar nenhum deles.

A referência é a qualidade de engenharia de produto e design, não a aparência específica.

---

# 38. IMPORTANTE: PRESERVAR FUNCIONALIDADE

Não quebrar:

* APIs
* banco de dados
* autenticação
* navegação
* campanhas
* catálogo
* IA
* conversas
* estados existentes
* ações
* integrações

Primeiro entender a arquitetura atual.

# 40. CRITÉRIO DE ACEITAÇÃO

Não considere a tarefa concluída apenas porque:

"não existem erros no console"

ou

"a aplicação funciona".

A tarefa só está concluída quando a interface também estiver visualmente consistente.

Quero uma revisão de **engenharia de design**, não apenas uma correção de CSS.

O objetivo final é:

**funcionalidade existente + arquitetura visual consistente + estados corretos + espaçamento correto + excelente experiência mobile + aparência premium.**
